Bạn sửa một dòng React rồi chờ giao diện cập nhật. Khi dự án lớn dần, khoảng chờ đó bắt đầu làm gián đoạn công việc. Chuyển từ webpack sang Vite có giải quyết được không? Có thể, nhưng trước hết cần biết mình đang chờ compiler, plugin, type checker hay browser tải module.

Bài này đi từ một lần mở trang đến một lần sửa code, rồi mới so sánh production build. Mục tiêu là giúp bạn giải thích được vì sao hai toolchain có hành vi khác nhau và biết kiểm tra gì trước khi đổi công cụ. Đây là bài giải thích kỹ thuật, không phải bộ câu hỏi phỏng vấn.

<Callout type="info" title="Phạm vi phiên bản và kiến thức nền">

Bài dùng **Vite 8** và **webpack 5** làm mốc. Vite 8 dùng Rolldown cho bundling và dependency optimization, cùng Oxc cho các tác vụ transform JavaScript/TypeScript. Mô tả “esbuild khi dev, Rollup khi build” thuộc toolchain Vite đời trước, không nên dùng để giải thích mọi phiên bản.

Bạn chỉ cần quen `import`, React component và script trong `package.json`. Nếu chưa rõ compiler khác bundler thế nào, đọc [bản đồ frontend build tooling](/web/02-frontend-build-tooling) trước.

## So sánh hai toolchain, không chỉ hai bundler

Giả sử `npm run dev` chạy `vite`. Một lệnh đó khởi động dev server, xử lý HTML, transform source, phục vụ CSS/assets và kết nối cơ chế cập nhật code. Vite là **build tool**: nó tổ chức nhiều công cụ bên dưới thành một workflow cho ứng dụng.

webpack tập trung vào **bundling**: lần theo các import và tổ chức module thành những file đầu ra. Để có trải nghiệm tương tự cho React/TypeScript, bạn thường dùng thêm `webpack-dev-server`, loader xử lý TypeScript/CSS và plugin tạo HTML. Loader chuyển đổi từng loại module; plugin can thiệp vào các giai đoạn của quá trình build.

Vì vậy, đối tượng so sánh thực tế là **Vite cùng plugin framework** với **webpack cùng loaders, plugins và dev server**. Nếu một bên có type checking còn bên kia không có, thời gian đo được chưa phản ánh cùng khối lượng công việc.

| Câu hỏi | Vite 8 | Toolchain webpack 5 |
| --- | --- | --- |
| Ai điều phối workflow? | Vite cung cấp dev/build CLI và nhiều mặc định cho ứng dụng web | webpack kết hợp các công cụ được chọn trong cấu hình |
| App source trong dev mặc định | Phục vụ dưới dạng native ES modules, transform theo request | Compile graph từ entry và phục vụ bundles/chunks |
| Engine bundling | Rolldown; không phải webpack | webpack |
| Xử lý framework | Plugin tương ứng, chẳng hạn `@vitejs/plugin-react` | Loaders/plugins tương ứng; cấu hình React Refresh riêng nếu cần |
| Production output | Bundle, chunks, CSS/assets theo cấu hình build | Bundle, chunks, CSS/assets theo cấu hình build |
| HMR | Có; phụ thuộc module boundary và plugin | Có; phụ thuộc module boundary và tích hợp framework |

Đừng hiểu bảng này thành “Vite không bundle” hay “webpack chỉ xuất một file”. Hai kết luận đó đều bỏ qua phần quan trọng của pipeline.

## Một ứng dụng để theo dõi xuyên suốt

Mình dùng một màn hình React có hai việc rất nhỏ:

- Vừa mở trang, bạn thấy dòng **Kết quả: 5**.
- Khi bấm nút **Tải admin module**, bạn mới thấy thêm dòng **Admin module đã được tải**.

Ta sẽ xem code tạo ra hai hành vi này. Trong ví dụ, một **module** là một file code có thể chia sẻ hàm hoặc component cho file khác bằng `export` và `import`.

### Từ HTML đến React component

Browser mở `index.html` trước. Trong phần body của file này có:

```html
<div id="root"></div>
<script type="module" src="/src/main.tsx"></script>
```

`div` là chỗ để React gắn giao diện vào. Thẻ `script` yêu cầu browser tải code từ URL `/src/main.tsx`; `type="module"` cho phép script dùng cơ chế `import` của JavaScript.

Đây là HTML dùng với **Vite dev server**, không phải file có thể mở trực tiếp rồi mong browser chạy TSX. Vite nhận request tới `main.tsx`, chuyển TSX thành JavaScript rồi mới trả về browser. Phần sau sẽ giải thích bước chuyển đổi này; ở đây chỉ cần nhớ browser vẫn chạy JavaScript.

File `src/main.tsx` có nội dung:

```tsx
import { createRoot } from 'react-dom/client';
import App from './App';
import './styles.css';

const element = document.getElementById('root');
if (!element) throw new Error('Missing #root');
createRoot(element).render(<App />);
```

Đoạn cuối tìm vùng `root` trong HTML rồi yêu cầu React hiển thị component `App` vào đó. `import App from './App'` lấy component này từ file `src/App.tsx`. Vậy giao diện bạn nhìn thấy sẽ do `App` quyết định, không phải do thẻ `script` tự tạo ra.

### Lúc mở trang và lúc bấm nút

Đây là toàn bộ `src/App.tsx`, chỉ bỏ các comment đánh dấu vùng source:

```tsx
import { useState } from 'react';
import { sum } from './math';

export default function App() {
  const [message, setMessage] = useState<string | null>(null);

  async function openAdmin() {
    const { getAdminMessage } = await import('./admin');
    setMessage(getAdminMessage());
  }

  return (
    <main>
      <h1>Frontend build lab</h1>
      <p>Kết quả: {sum(2, 3)}</p>
      <button onClick={openAdmin}>Tải admin module</button>
      {message && <p role="status">{message}</p>}
    </main>
  );
}
```

Đọc lần đầu, bạn chỉ cần theo dõi hai thời điểm.

**Khi vừa mở trang:** React chạy component `App` để tạo giao diện. Biểu thức `sum(2, 3)` gọi hàm cộng lấy từ `math.ts`, trả về `5`. Vì vậy dòng đầu hiển thị `Kết quả: 5`.

`message` là giá trị mà React giữ giữa các lần cập nhật giao diện, thường gọi là **state**. Ban đầu nó là `null`, tức chưa có thông báo. Dòng `{message && ...}` chỉ hiển thị đoạn thông báo khi `message` có giá trị, nên lúc này bạn chưa thấy dòng nào bên dưới nút.

Còn `openAdmin` thì sao? Component mới chỉ khai báo hàm đó. `onClick={openAdmin}` đăng ký hàm làm thao tác xử lý khi bấm nút; nó **không gọi hàm ngay trong lúc tạo giao diện**. Vì thế, dòng `import('./admin')` bên trong chưa chạy.

**Khi bạn bấm nút:** React gọi `openAdmin`. Dòng `await import('./admin')` bắt đầu nạp module `admin.ts` và chờ lấy được các giá trị mà module export. Code lấy ra hàm `getAdminMessage`, gọi hàm để nhận chuỗi `Admin module đã được tải`, rồi đưa chuỗi đó vào `setMessage`.

`setMessage` là hàm cập nhật state. React dùng giá trị mới để cập nhật giao diện; lúc này bạn mới thấy thông báo bên dưới nút. Lần bấm tiếp theo không nhất thiết tải lại code qua mạng vì module đã được nạp có thể được dùng lại.

### Static import và dynamic import khác nhau ở đâu?

Sau khi đã thấy luồng chạy, ta mới đặt tên cho hai cách import:

```ts
import { sum } from './math'; // Static import
```

**Static import** khai báo dependency ở cấp ngoài cùng của file. Module `App` cần dependency `math` sẵn sàng trước khi phần code của chính nó được thực thi. Trong ví dụ này, phép tính cần dùng ngay trên màn hình đầu tiên, nên cách viết đó phù hợp.

Lưu ý: **import hàm không có nghĩa là gọi hàm**. Dòng import lấy hàm `sum`; biểu thức `sum(2, 3)` trong phần giao diện mới gọi hàm để tính ra `5`.

```ts
const { getAdminMessage } = await import('./admin'); // Dynamic import
```

**Dynamic import** là biểu thức có thể đặt bên trong hàm. Nó chỉ bắt đầu nạp module khi luồng chạy đến biểu thức đó. `import()` trả về một **Promise**, tức đối tượng đại diện cho kết quả sẽ có sau; `await` chờ kết quả đó trước khi chạy dòng tiếp theo trong hàm.

Ở đây, chính việc đặt `import('./admin')` trong hàm xử lý nút bấm giúp trì hoãn nạp module admin. Không phải cứ viết `import()` là code tự chờ người dùng: nếu đặt biểu thức đó ở chỗ chạy ngay lúc khởi động, nó vẫn bắt đầu nạp ngay lúc khởi động.

| Thời điểm trong ví dụ | Module math | Module admin |
| --- | --- | --- |
| Mở trang lần đầu | Cần sẵn sàng để App tính và hiển thị `5` | Chưa được yêu cầu qua `import('./admin')` |
| Bấm nút tải admin | Đã được nạp | Bắt đầu được nạp, rồi cung cấp hàm tạo thông báo |

**Điểm cần giữ để đọc tiếp:** app cần code tính toán ngay khi mở trang, còn code admin chỉ cần sau khi bấm nút. Vite và webpack đều hỗ trợ cách viết này. Phần tiếp theo so sánh cách mỗi toolchain đưa những module đó đến browser.

Bạn có thể mở lại <SourceRef project="frontend-build-lab" file="src/App.tsx" region="lazy-import">hàm openAdmin trong React component</SourceRef> để đối chiếu source. Các bước chạy lab nằm ở phần thực hành bên dưới.

## webpack làm gì khi mở trang lần đầu?

### Từ entry đến bundle có runtime

Với cấu hình webpack thông thường, entry là `src/main.tsx`. Compiler đọc file đó, tìm các import và xây **module graph** — danh sách module cùng quan hệ phụ thuộc giữa chúng. Khi gặp TSX hay CSS, webpack gọi loader phù hợp trước khi tiếp tục xử lý.

Sơ đồ này mô tả đường đi của code trong dev, không phải số request cố định hay một phép đo thời gian:

```d2 interactive=false title="webpack dev: compiler tạo bundles trước khi browser thực thi app"
direction: down
source: "Entry và các module được import"
compiler: "webpack compiler" {
  icon: ../../diagrams/assets/webpack.svg
}
assets: "Bundles / chunks và webpack runtime"
server: "webpack-dev-server"
browser: "Browser chạy ứng dụng"
source -> compiler: "Resolve imports, chạy loaders/plugins"
compiler -> assets: "Tạo output theo chunk graph"
assets -> server: "Phục vụ output, thường từ memory"
server -> browser: "HTML và các assets được yêu cầu"
```

**Chunk** là đơn vị webpack dùng để nhóm code khi tạo output. Browser không nhất thiết tải mọi chunk ngay lúc mở trang. Chẳng hạn, chunk của `import('./admin')` có thể chỉ được tải khi hàm `openAdmin` chạy.

Bundle còn có **runtime**, tức phần code quản lý việc thực thi module và tải thêm chunk. Vì thế, nhìn thấy một file JavaScript trong Network không có nghĩa file đó tương ứng một-một với một file source.

`webpack-dev-server` thường phục vụ kết quả compile từ bộ nhớ. Không thấy bundle mới trên ổ đĩa chưa đủ để kết luận compiler không chạy.

### Compile lại không có nghĩa làm lại mọi thứ

Khi `App.tsx` thay đổi, webpack có thể dùng kết quả đã cache cho những module không đổi. Compiler đang watch cũng giữ thông tin giữa các lần rebuild. Nếu bật filesystem cache, một phần kết quả có thể được dùng lại qua các lần khởi động process.

Chẳng hạn, một cấu hình muốn cache xuống đĩa có thể thêm:

```js
cache: {
  type: 'filesystem',
  buildDependencies: {
    config: [__filename],
  },
},
```

Đây là một phần của `webpack.config.cjs`, không phải cấu hình đầy đủ. Khai báo file config trong `buildDependencies` giúp cache biết khi nào cấu hình build thay đổi.

Chi phí rebuild vẫn phụ thuộc vào phạm vi module bị ảnh hưởng và công việc của loaders/plugins. Nhưng nói “mỗi lần sửa là webpack compile lại toàn bộ dự án từ đầu” sẽ dẫn bạn đến chẩn đoán sai. Trước khi migrate, kiểm tra cache, source map và các tác vụ chạy lại trong mỗi compilation.

## Vite làm gì khi mở trang lần đầu?

### Browser yêu cầu module, server transform theo nhu cầu

Ở chế độ dev native ESM mặc định, browser đọc `index.html` rồi yêu cầu `/src/main.tsx`. Vite transform TSX thành JavaScript, xử lý đường dẫn import và trả kết quả. Browser đọc các import trong response rồi tiếp tục yêu cầu module cần thiết.

**Native ESM** nghĩa là browser dùng cơ chế ES modules của chính nó để nạp code. Nó không có nghĩa browser tự hiểu TypeScript, JSX hoặc cách tìm package trong `node_modules`.

Sơ đồ dưới đây tách app source khỏi dependency ít thay đổi:

```d2 interactive=false title="Vite dev: phục vụ source theo request, tối ưu dependency riêng"

```

Nếu chưa bấm nút tải admin, browser chưa cần module đó theo đường thực thi của ví dụ. Vite không phải tạo một production bundle của toàn app trước khi phục vụ trang này.

Tuy nhiên, Vite vẫn có bước khởi tạo plugin, phân tích import và khám phá dependency. **Theo nhu cầu không có nghĩa là hoàn toàn không đọc source trước request đầu tiên.** Điểm khác biệt là cách tổ chức việc transform và phục vụ app source, không phải loại bỏ mọi bước chuẩn bị.

### Vì sao vẫn cần pre-bundle dependency?

Dòng `import { useState } from 'react'` dùng một **bare import**: tên package chứ không phải URL tương đối hay tuyệt đối. Trong workflow này, Vite resolve package và rewrite import sang URL mà browser tải được.

Vite còn **pre-bundle dependency**, tức xử lý trước một nhóm dependency thành output phù hợp để phục vụ trong dev. Có hai lý do chính:

- Package phát hành dưới dạng CommonJS hoặc UMD cần được chuyển thành ESM.
- Package ESM gồm rất nhiều file nhỏ có thể làm browser phát sinh quá nhiều request. Gom chúng lại giúp giảm chi phí nạp trang.

Vite 8 dùng Rolldown cho bước này và mặc định cache kết quả ở `node_modules/.vite`. Nó có thể tối ưu lại khi lockfile hoặc cấu hình liên quan thay đổi. Dependency mới chỉ được phát hiện sau một plugin transform cũng có thể kích hoạt thêm một lượt tối ưu.

Đây là lý do câu “Vite dev hoàn toàn không bundling” không đúng. Chính xác hơn: **app source được phục vụ theo native ESM trong chế độ này, còn dependency có pipeline tối ưu riêng**.

### Khởi động nhanh khác với trang sẵn sàng nhanh

Một dev server có thể báo sẵn sàng rất sớm, nhưng browser vẫn phải yêu cầu và thực thi module trước khi giao diện dùng được. Giả sử một route import nối tiếp nhiều module, request sau chỉ được phát hiện khi response trước đã về. Độ sâu của chuỗi import cũng có thể tạo khoảng chờ.

Vì vậy, cần đo cả thời gian process khởi động lẫn thời gian trang tương tác được. Với codebase rất lớn, số request module trong dev có thể trở thành vấn đề riêng.

<Callout type="info" title="Không biến mô hình mặc định thành quy luật bất biến">

Thông báo Vite 8 giới thiệu hướng **Full Bundle Mode** ở trạng thái experimental: bundle code trong dev để giảm số request. Bài này giải thích luồng native ESM mặc định, không dùng chế độ thử nghiệm đó làm cơ sở so sánh. Khi đọc một dự án khác, kiểm tra cả phiên bản lẫn mode thực tế.

</Callout>

## Sửa một file thì HMR đi đến đâu?

Giả sử bạn sửa chữ trong `App.tsx` trong khi trang đang mở. **Hot Module Replacement (HMR)** là cơ chế đưa code mới vào ứng dụng đang chạy mà không cần tải lại toàn bộ document.

Trong Vite native ESM dev, server đánh dấu kết quả transform liên quan là không còn hợp lệ và thông báo cho client. Client tải module cập nhật. Trong webpack, compiler tạo dữ liệu cập nhật cho compilation mới; HMR runtime tải và áp dụng các module thay đổi. Không phải mỗi lần webpack HMR đều gửi lại toàn bộ app bundle.

Cả hai cần một **HMR boundary** — nơi chấp nhận bản cập nhật và biết cách áp dụng nó an toàn. Nếu module thay đổi không tự xử lý được, việc cập nhật có thể lan tới các module import nó. Khi không tìm được boundary thích hợp, toolchain có thể phải reload trang.

Điều này giải thích vì sao sửa một component và sửa một module cấu hình dùng chung có thể cho trải nghiệm rất khác nhau. Số dòng sửa ít không đảm bảo phạm vi ảnh hưởng nhỏ.

### HMR không tự đảm bảo giữ React state

Bạn bấm nút trong app để tạo một ít state, rồi sửa nhãn trên giao diện. Muốn nhãn cập nhật mà state còn nguyên, cần tích hợp framework hiểu cách thay component. Với React, phần này thường là **Fast Refresh**, được nối vào HMR bởi plugin tương ứng.

Vite có `@vitejs/plugin-react` cho workflow React. webpack cũng có thể tích hợp React Refresh; chỉ bật `devServer.hot` không tự biến mọi module React thành một boundary giữ state.

Ngay cả khi có Fast Refresh, một số thay đổi vẫn có thể reset state hoặc dẫn tới reload. Ví dụ, thay cấu trúc hooks không tương đương với sửa một chuỗi văn bản. Vì vậy, khi kiểm tra HMR, hãy chọn cùng loại thay đổi ở cả hai toolchain.

<Callout type="warn" title="Phân biệt khả năng của tool với cấu hình ví dụ">

Demo webpack ở [bài trước](/web/03-webpack-tu-source-den-trinh-duyet) cố ý đặt `hot: false` và `liveReload: true`. Khi demo đó reload cả trang, bạn đang quan sát cấu hình live reload, không phải giới hạn của webpack. Đừng dùng nó làm benchmark đối đầu với React Fast Refresh của Vite.

</Callout>

## Production vẫn cần một pipeline riêng

Native ESM giúp dev server phục vụ source linh hoạt. Nhưng trên đường truyền tới người dùng, hàng loạt file nhỏ và chuỗi import sâu có thể tạo nhiều lượt chờ. Production build tổ chức lại code để phục vụ hiệu quả hơn, thay vì đơn giản copy các module dev lên hosting.

Với Vite 8, `vite build` dùng Rolldown. Với webpack, build production vẫn do webpack điều phối theo cấu hình tương ứng. Cả hai có thể tạo nhiều chunks, rút gọn code và xử lý assets; chất lượng output còn phụ thuộc cách bạn viết app và cấu hình pipeline.

### Bundling, tree shaking và code splitting khác nhau

Quay lại ví dụ `sum` và `openAdmin`:

| Công việc | Ý nghĩa trong ví dụ | Không nên suy ra |
| --- | --- | --- |
| Bundling | Gom và tổ chức các module thành output để phân phối | Luôn gom tất cả vào một file |
| Tree shaking | Loại code không dùng nếu có thể chứng minh việc bỏ đó là an toàn | Mọi dòng “có vẻ không được gọi” đều bị xóa |
| Code splitting | Tạo phần output có thể tải riêng, chẳng hạn admin qua `import()` | Mỗi component chắc chắn có một chunk riêng |
| Minification | Rút gọn biểu diễn code trong output | Tự thay thế được ba công việc trên |

Trong lab, `math.ts` còn export `unusedMessage`, nhưng app không import hàm này. Production build có thể loại hàm đó. Nếu module có side effect — chẳng hạn đăng ký event listener ngay khi được import — bundler phải xét xem việc bỏ module có thay đổi hành vi không.

`import('./admin')` tạo một ranh giới tải bất đồng bộ trong ví dụ. Hình dạng chunk cuối cùng còn phụ thuộc các import khác và cách bundler chia shared code. Trong app khác, nếu admin đã được static import ở đường khởi động, bạn không còn được hưởng việc trì hoãn tải phần code đó chỉ nhờ thêm một dynamic import nữa.

### Dùng chung engine không làm dev giống production

Vite 8 thống nhất nhiều phần xử lý quanh Rolldown/Oxc, nhưng điều đó không làm `vite dev` và `vite build` trở thành cùng một tác vụ. Dev có HMR và cách phục vụ module riêng. Build có bước tổ chức output, tối ưu và thay giá trị cấu hình dành cho bản phát hành.

Mốc phiên bản giúp bạn đọc các bài hướng dẫn cũ đúng ngữ cảnh:

| Toolchain | Dependency pre-bundling trong dev | Production bundling |
| --- | --- | --- |
| Vite 7 bản tiêu chuẩn | esbuild | Rollup |
| Vite 8 | Rolldown | Rolldown |

Bảng không bao gồm bản chuyển tiếp `rolldown-vite` hay cấu hình thay thế. Muốn biết dự án đang dùng gì, kiểm tra lockfile và lệnh build thay vì đoán từ tên file `vite.config.ts`.

## TypeScript chạy được chưa chắc đúng type

Giả sử một hàm khai báo trả về `number` nhưng lại trả về chuỗi:

```ts
export function sum(a: number, b: number): number {
  return String(a + b);
}
```

Đoạn này có lỗi type, nhưng sau khi bỏ type annotation, nó vẫn là JavaScript hợp lệ. **Transform TypeScript không đồng nghĩa với type checking.** Vite transform file để phục vụ/build; nó không tự kiểm tra toàn bộ hệ thống kiểu của ứng dụng.

Lab tách trách nhiệm bằng các script sau:

```json
{
  "scripts": {
    "typecheck": "tsc --noEmit",
    "build": "npm run typecheck && vite build"
  }
}
```

Type checker thất bại thì `&&` ngăn bước build tiếp tục. Khi dev, bạn có thể chạy `tsc --noEmit --watch` trong một terminal khác để nhận lỗi liên tục.

Ở webpack, hành vi phụ thuộc loader và cấu hình. `ts-loader` có thể type-check; nếu dùng `transpileOnly`, SWC hoặc Babel để chỉ transform, bạn cần một tác vụ type checking riêng. Khi so tốc độ, hãy đối chiếu trách nhiệm này trước.

## Thực hành bằng source có sẵn

Lab dưới đây đã nằm trong repository `interview-question`, không cần tạo app mới hoặc chép các đoạn trích thành một project khác.

<SourceRef project="frontend-build-lab" file="vite.config.ts" variant="button">Mở toàn bộ source · Vite React/TypeScript lab</SourceRef>

Chạy các lệnh sau từ thư mục `interview-question`. Lab khai báo Node.js từ `22.12.0`; dùng một bản Node đáp ứng yêu cầu engine của dependencies được cài. Lab không có lockfile được commit, nên `npm install` ở các thời điểm khác nhau có thể resolve patch/minor khác nhau; đây không phải bộ fixture benchmark đã pin.

### Quan sát native ESM và cập nhật component

```bash
cd examples/frontend-build-lab
npm install
npm run dev -- --port 5173 --strictPort
```

Mở `http://127.0.0.1:5173`, rồi mở Network trong DevTools. Với lần nạp đầu không dùng browser cache, bạn sẽ thấy request source như `/src/main.tsx` cùng các module liên quan. Mở response TSX để kiểm tra: nội dung trả về đã là JavaScript, không phải browser tự parse type annotation.

Bấm **Tải admin module**. App hiển thị `Admin module đã được tải`. Theo dõi request xuất hiện khi thao tác này chạy; đừng chỉ tìm tên file rồi giả định thời điểm tải.

Giữ nguyên trang, sửa tiêu đề `Frontend build lab` trong `src/App.tsx` thành một chuỗi khác. Với thay đổi văn bản này, giao diện cập nhật và thông báo admin vẫn còn. Bạn vừa kiểm tra một trường hợp Fast Refresh giữ state, không chứng minh mọi thay đổi đều giữ state.

### Đối chiếu production chunks và manifest

Dừng dev server. Từ chính thư mục lab, chạy:

```bash
npm run build
npm run preview -- --port 4173 --strictPort
```

Mở `http://127.0.0.1:4173`. Preview phục vụ output đã build; nó không tiếp tục transform source như dev server và không phải production server được khuyến nghị để triển khai thực tế.

Lab bật `build.manifest: true` trong <SourceRef project="frontend-build-lab" file="vite.config.ts">vite.config.ts</SourceRef>. Đọc `dist/.vite/manifest.json`, tìm entry `src/admin.ts` và trường `file` để biết tên chunk được tạo. Tên hash là kết quả của lần build, không phải một hằng số cần chép vào code.

Reload trang với Network đang ghi request. Đối chiếu ba điều:

1. Trang đầu hiển thị `Kết quả: 5`.
2. Chunk admin ghi trong manifest chưa được tải trước thao tác trong lab này.
3. Bấm nút mới yêu cầu chunk đó và hiển thị thông báo admin.

Sau đó tìm chuỗi `UNUSED_MATH_SENTINEL` trong các file JavaScript runtime của `dist/assets`. Chuỗi nằm trong hàm không được dùng ở source, và phải vắng mặt trong output của lab. Đây là phép kiểm tra cụ thể cho tree shaking của ví dụ, không phải bảo đảm rằng mọi dependency trong một ứng dụng đều tree-shake được.

### Tách lỗi type khỏi lỗi transform

Dừng preview. Trong <SourceRef project="frontend-build-lab" file="src/math.ts">src/math.ts</SourceRef>, đổi `return a + b` thành `return String(a + b)` nhưng giữ kiểu trả về `number`. Chạy từng lệnh riêng để thấy khác biệt:

Với thay đổi này, kết quả cần đối chiếu là:

| Lệnh | Kết quả cần quan sát | Lý do |
| --- | --- | --- |
| `npm run typecheck` | Báo lỗi type, exit code khác 0 | Giá trị trả về là string, không khớp number |

Đây là các kết quả mong đợi để bạn tự kiểm tra, không phải log terminal giả lập. Sửa lại `return a + b` và build lại sau thử nghiệm để không giữ output của phiên bản sai type.

## Những khác biệt phải xử lý khi chuyển từ webpack

Giả sử app đang dùng `process.env.API_URL`, alias `@/`, import SVG thành React component và được host dưới `/portal/`. Chép source sang Vite chưa giải quyết được bốn quy ước đó. Toolchain mới cần tạo ra cùng hành vi, chứ không cần có một file config trông giống file cũ.

| Vùng cần kiểm tra | Với Vite | Điều cần giữ đúng khi migrate |
| --- | --- | --- |
| HTML entry | HTML thuộc pipeline; khai báo module script | Không copy nguyên giả định của `HtmlWebpackPlugin` |
| Environment variables | Mặc định dùng `import.meta.env.VITE_*` cho giá trị custom ở client | Đối chiếu chỗ đang dùng DefinePlugin hoặc env replacement của webpack |
| Alias và extension resolution | Cấu hình tương ứng trong Vite và công cụ liên quan | Alias trong TypeScript không tự chứng minh runtime resolve đúng |
| CSS, SVG và asset imports | Dùng hành vi mặc định hoặc plugin thích hợp | Phân biệt URL asset, raw text và React component |
| CommonJS và Node APIs | Dependency optimizer xử lý nhiều package CommonJS trong dev | `node:fs` không tự có bản tương đương trong browser |
| Đường dẫn deploy | `base` ảnh hưởng URLs của assets | Đối chiếu `output.publicPath`; test cả dynamic chunks |
| Dev proxy và routing | Có cấu hình dev server riêng | Dev proxy không tự trở thành production proxy hay SPA fallback của hosting |
| Module Federation | Cần chọn tích hợp tương thích cụ thể | Không mặc định plugin Vite là bản thay thế trực tiếp cho webpack ModuleFederationPlugin |

Với `/portal/`, hãy kiểm tra cả HTML, ảnh/CSS, URL chunk admin và refresh một deep link sau production build. Router base, asset base và cấu hình fallback của hosting là những trách nhiệm liên quan nhưng không thay thế nhau.

**Không đặt secrets vào biến môi trường được đưa xuống client.** Prefix `VITE_` chỉ là quy ước chọn biến để expose, không phải cơ chế bảo mật. Giá trị được nhúng vào bundle có thể bị người dùng đọc; webpack DefinePlugin cũng không biến client code thành nơi giữ bí mật.

Loader của webpack không được chuyển sang Vite chỉ bằng đổi tên thành plugin. Nếu app có transform riêng cho SVG, i18n hoặc code generation, mình sẽ kiểm tra các phần đó sớm: chúng thường quyết định migration có khả thi hơn là vài dòng config entry/output.

## Đo trước khi kết luận công cụ nào nhanh hơn

Giả sử Vite báo server ready sớm hơn, nhưng route chính vẫn mất lâu để dùng được. Nếu chỉ ghi số ở terminal, bạn sẽ bỏ qua chi phí transform, request và thực thi phía browser. Chọn mốc đo theo công việc của người phát triển, không chỉ theo thông báo của CLI.

| Phép đo | Điểm bắt đầu và kết thúc | Điều kiện cần ghi lại |
| --- | --- | --- |
| Cold start | Khởi động process đến lúc route kiểm tra tương tác được | Trạng thái tool cache và browser cache; dependency đã cài hay chưa |
| Warm start | Khởi động lại đến cùng mốc tương tác | Cache nào còn được giữ |
| Component update | Lưu cùng thay đổi đến lúc DOM cập nhật | Loại sửa, trạng thái HMR/Fast Refresh, có reload hay không |
| Shared-module update | Sửa module dùng chung đến giao diện cập nhật | Những route/module bị ảnh hưởng |
| Production build | Bắt đầu script đến lúc hoàn tất cùng tập kiểm tra và output | Type checking, source map, minification, plugins |
| Production loading | Điều hướng đến mốc tương tác đã chọn | Kích thước tải, số request, cache và network/CPU profile |

Giữ cùng source, cùng browser targets và cùng trách nhiệm kiểm tra. Lặp lại phép đo, ghi phiên bản Node/tool/dependencies rồi so cả phân bố kết quả thay vì chọn một lượt nhanh nhất.

Nếu dùng hai lab khác source, bạn vẫn có thể học cách mỗi pipeline hoạt động. Nhưng không thể dùng thời gian của chúng làm bằng chứng “Vite nhanh hơn webpack bao nhiêu lần”. Bài này không đưa ra benchmark vì chưa có phép so sánh đối chứng như vậy.

## Khi nào chọn Vite, khi nào giữ webpack?

Với một React/Vue SPA mới, không có ràng buộc đặc biệt từ framework, mình chọn Vite làm điểm bắt đầu. Các mặc định cho HTML, assets và dev server giúp giảm phần cấu hình cần tự ghép. Sau đó vẫn cần type checking, tests và kiểm tra production output.

Với app webpack đang ổn định, mình không đổi tool chỉ vì tên công cụ mới hơn. Trước hết hãy xác định chỗ chậm và thử xử lý đúng nút thắt. Nếu app phụ thuộc loader/plugin chuyên biệt, Federation runtime hoặc quy trình build đã tích hợp sâu, chi phí chuyển đổi phải được tính cùng lợi ích thực tế.

Nếu đã chọn một framework có build system riêng như Next.js, hãy theo workflow của framework trước. Đổi bundler không đơn giản là thay script `next build` bằng `vite build`: routing, server rendering và output contract cũng thay đổi.

Một bước thử hợp lý là chuyển một route đại diện hoặc một bản app thử nghiệm sang Vite. Route đó nên có dependency thật, CSS/assets, lazy loading và environment variables. Chỉ cân nhắc chuyển toàn bộ sau khi dev workflow, production build và cách host đều được kiểm chứng.
